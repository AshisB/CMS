# Canteen Management System (CMS)
### Feasibility Study — Version 1.0 (Draft)

**Date:** September 2026
**Based on:** requirement-analysis.md

---

## 1. Purpose

This study checks whether building the CMS as scoped in the Requirement Analysis is realistic for this team, this canteen, and this budget — before time is spent on design and implementation.

## 2. Technical Feasibility

**Assessment: Feasible, with expected learning curve.**

- Team has basic Python/Flask knowledge and will learn further concepts (HTMX, Podman, TOTP integration) while building — this is an accepted and intentional part of the project's purpose.
- Risk: as a "learn while building" project, timelines should assume slower initial velocity, especially in Phase 1 (account/allowance model) before the team finds its rhythm.
- Mitigation: the phased build order already defined (individual accounts → department budgets → in-charge dashboard/TOTP) keeps each stage small enough to learn from without blocking the whole project on one hard problem.

## 3. Operational Feasibility

**Assessment: Not currently feasible without a hardware/training plan — this is the project's main risk.**

- Canteen staff currently track everything on paper and are not established as tech-savvy users.
- No devices (PC/tablet at the counter, or staff phones) currently exist for this workflow.
- This is a real adoption barrier, not a minor detail — a system nobody can physically use at the counter does not solve the problem, regardless of how well it's built.

**Mitigation plan for V1:**
- Convince canteen/admin to provide or bring one laptop/tablet at the order counter to start — a single-device pilot is enough for V1, no need for a device per staff member.
- Keep the counter-facing UI (Admin/Order Taker view) as simple as possible — large buttons, minimal typing — specifically because the primary users are not tech-savvy. This should directly inform system design later.
- Use color-coded order status so staff can read state at a glance without reading text: 🔴 Red = urgent/new, 🟡 Yellow = processing, 🟢 Green = ready/completed.
- Run a short, hands-on training session with canteen staff before rollout rather than assuming a dashboard is self-explanatory.
- Treat V1 as a **pilot with one canteen counter**, not a full rollout, so problems surface on a small scale first.

## 4. Economic Feasibility

**Assessment: Feasible — zero budget confirmed, self-hosted only.**

- No budget currently available; the system must run on free-tier/self-hosted infrastructure.
- This directly supports the stack already chosen: Python/Flask + HTMX (lightweight, no paid frontend build/hosting pipeline) and Podman (free, self-hosted containers — no cloud hosting bill).
- Practical implication: hosting will likely be on an existing office machine or a free-tier VM, not a paid cloud service. This should be treated as a hard constraint in system design, not an afterthought.

## 5. Future Direction (Noted, Not Designed For Yet)

Two ideas came up that are valuable but **out of scope for V1** and should not influence current design decisions:

- **Multi-calendar support** — showing the English (Gregorian) date alongside the Nepali calendar. Straightforward to add later; not urgent for a single-office pilot.
- **Nepali language/font support** — full localization of the interface, not just dates. Pairs naturally with the multi-calendar addition above; worth doing together in the same later phase.
- **Selling the CMS to other canteens / offering it online** — a genuine long-term possibility if the internal pilot succeeds, but designing for multi-tenant/commercial use now would significantly complicate V1 for no immediate benefit. Revisit this only after the internal pilot proves the core workflow actually works.

## 6. Overall Recommendation

**Proceed**, on the condition that operational feasibility is treated as seriously as the technical build:

1. Secure at least one device for the canteen counter before/alongside development, not after.
2. Design the counter-facing UI for non-technical users from the start (this belongs in the System Design phase next).
3. Keep V1 scoped to a single-canteen pilot — no multi-tenant or commercial features yet.
4. Budget stays at zero — all tooling choices (Flask, HTMX, Podman) already respect this.
